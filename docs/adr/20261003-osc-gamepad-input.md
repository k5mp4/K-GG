# ADR-20261003-osc-gamepad-input: OSC入力はRust側のループバックUDPで受信する

## コンテキスト

GameCubeコントローラーアダプターの入力をOSCへ変換する外部ツール（kg_GCcontroller）で、K-GGのPreset選択などを操作したい。OSCはUDPで届くが、WebViewのRendererはUDPソケットを開けない。外部から届く値は信頼できず、LAN上の他の機器から操作されることも避けたい。

## 決定

1. OSCの受信はTauriのRust側だけで行い、Web版では提供しない。
2. `127.0.0.1`の指定UDPポート（既定9000、1024以上）へバインドする。有効/無効とポートはRendererの設定（SANDBOXのController）からTauriコマンドで切り替え、既定は無効とする。バインドに失敗してもアプリの動作は妨げず、結果を状態として返す。
3. Rustでパケットを検証し、数値引数だけを持つメッセージに限定してRendererへ`kgg-osc`イベントで送る。アドレス長、引数数、1回に転送するメッセージ数、bundleの入れ子に上限を設ける。型タグのないメッセージ、非有限の値、不正なbundleは捨てる。
4. 約16msごとに受信分をまとめて1イベントにする。
5. OSCアドレスからアプリ操作への変換（スティックの方向判定、リピート、ボタンの立ち上がり検出、割り当て）はRendererの純粋なロジックに置き、設定のマッピングを呼び出しごとに参照する。UI側は操作コマンドだけを受け取る。割り当ては固定の操作・入力・パラメータの一覧から選ぶ形にし、任意のOSCアドレスや任意のストアキーは指定できない。

## 理由

- ループバック限定にすると、ネットワーク越しの入力という新しい攻撃面を作らない。同じPC上のブリッジツールだけを対象にできる。
- 値の検証をRust境界で行えば、Rendererは信頼できる数値だけを扱える。
- スティックのような連続値は毎秒数百件届くため、まとめて転送してIPC回数を抑える。
- 変換ロジックをTauriとReactから切り離すと、実機なしで単体テストできる。

## 代替案

| 案 | 採用しなかった理由 |
| --- | --- |
| ブリッジをWebSocketやHTTPにする | 既存のkg_GCcontrollerを変更する必要があり、OSCを送る他のツールも使えなくなる。 |
| 全インターフェースで受信する | LAN上の機器から操作できてしまう。別PCからの入力が必要になった時に、設定項目として改めて判断する。 |
| Renderer側でGamepad APIを使う | GCアダプターはWinUSBで接続しておりOSへ標準ゲームパッドとして現れない。OSC入力という汎用の入口にもならない。 |
