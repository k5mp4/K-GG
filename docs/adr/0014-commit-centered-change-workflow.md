# ADR-0014: 承認済み変更パッケージをコミット単位の基本にする

## コンテキスト

会話中の細かな追加指示ごとにchangeディレクトリを作ると、同じ目的の実装・検証履歴が分散し、proposalやtasksの維持コストが増えます。一方で、独立した要求を無制限に同じchangeへ混ぜると、レビュー範囲と差分の責任が不明瞭になります。

## 判断案

Why／What／対象外／受け入れ条件がまとまった承認済み変更パッケージを、changeディレクトリとコミット準備の基本単位にします。同一パッケージの目的・影響範囲に収まる追加指示は既存文書へ追記し、ACを再検証します。スコープ、対象外、AC、利用者影響のいずれかを変更する要求は新しいchange候補へ分離し、必要なら再承認します。

コミット、push、Pull Requestはユーザーの明示依頼が必要です。この判断は文書管理のまとまりを定めるものであり、自動的なGit外部操作を許可しません。

## 代替案

- 会話ターンごとにchangeを作る: 履歴は細かくなるが、同じ目的の差分が分散し管理コストが高い。
- すべての期間の作業を1つのchangeへまとめる: 管理は簡単だが、独立した変更のレビューとArchiveが追跡できない。
- コミット単位をAIが自動判断してcommitする: 利便性はあるが、ユーザーのGit操作承認境界を越えるため採用しない。

## 状態

このADRは、Request-firstの分類とValidation Gate分離を定める[ADR-0019](./0019-request-first-development-lifecycle)によりsupersededとなった。過去の変更Packageを一つのコミットへまとめる考え方は履歴として残るが、すべての変更にPackageを要求する運用は採用しない。

## 結果

変更履歴は承認パッケージ単位で読みやすくなり、追加指示の取り込み基準も明確になります。実装者は追加指示が同一パッケージへ収まるかを毎回判定し、仕様を変える場合はレビューへ戻します。
