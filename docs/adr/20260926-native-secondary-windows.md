# ADR-20260926-native-secondary-windows: Tauriネイティブ別ウインドウの生成と状態同期

## コンテキスト

CHANGE-015では、Effect StackをTauriの`WebviewWindow`で別ウインドウ化すると16×16の極小ウインドウになり、Webviewがページを読み込まない問題が実機で再現した。`visible`、`center`、URL形式、事前定義を試しても解決せず、別ウインドウ化そのものを廃止した。

その後の調査で、原因の候補を特定した。メインウインドウは`tauri.conf.json`で`additionalBrowserArgs`（GPU優先指定など）を持つ。WebView2は、同じユーザーデータフォルダーを使うWebviewが異なるブラウザー引数で作られると環境の作成に失敗する。JSから引数を指定せずに作ったWebviewは既定の引数になるため、メインと不一致になり、空の極小ウインドウという症状と一致する。CHANGE-015の試行記録にはブラウザー引数の一致は含まれていない。

Gradient Ramp editorは当初から別ウインドウでの操作を想定しており、キャンバスを隠さずに編集できる別ウインドウが求められている。

## 決定

Tauri版で別ウインドウを作る場合は次の方式に統一する。

1. ウインドウはRustのasyncコマンドで作成する。JSの`new WebviewWindow()`は使わない。Windowsでは同期コマンド内でWebviewを作るとデッドロックするため、asyncにする。
2. 別ウインドウのWebviewには、メインウインドウ設定の`additionalBrowserArgs`をそのまま渡す。値は`tauri.conf.json`から読み、コード内へ複製しない。
3. 別ウインドウはメインウインドウを親（owner）とし、メインが破棄されたらRust側で閉じる。別ウインドウの破棄はRust側からメインへイベントで通知する。
4. 文書状態とUndo履歴の一次情報はメインウインドウのstoreに置く。別ウインドウのstoreは編集対象sliceの複製とし、双方向の変更はウインドウ宛てのTauriイベントで同期する。受信したpatchは送り返さない。送信は受信側のACKで流量制御し、未ACKのメッセージは常に1件までとする。待機中の変更は1つのpatchへ統合し（キーごとに最新値を優先）、受信側は適用して1フレーム描画した後にACKを返す。Undo/Redoはメインへ依頼する。
5. 別ウインドウ用capabilityは、そのウインドウlabelに限定したファイルへ分け、必要なイベント・ウインドウ操作だけを許可する。
6. 同じフロントエンドbundleを使い、`main.tsx`でウインドウlabelにより読み込むルートを切り替える。別ウインドウではレンダラーとワークスペースを読み込まない。

ブラウザー版では別ウインドウを作らず、既存のインライン表示を使う。ネイティブウインドウの作成に失敗した場合もインライン表示へ戻す。

## 理由

- ブラウザー引数を一致させると、WebView2の環境共有の制約を満たしつつ、メインのGPU設定を別ウインドウにも適用できる。
- Rust側で作成すると、引数・親子関係・閉じる処理を1か所で管理でき、JSへ`create-webview-window`権限を渡す必要がない。
- storeの一次情報をメインに置くと、Preset保存、書き出し、Undo履歴、レンダラーは既存のまま動き、別ウインドウは編集UIだけを担える。

## 代替案

| 案 | 採用しなかった理由 |
| --- | --- |
| JSの`WebviewWindow`で作成し`additionalBrowserArgs`を指定 | 引数をJSへ複製する必要があり、作成権限を常時JSへ渡す。CHANGE-015で失敗した経路と区別しにくい。 |
| 別ウインドウ用に別のユーザーデータフォルダーを使う | localStorage（パレット、言語設定）が共有されず、プロセスとメモリも増える。 |
| Document Picture-in-Picture／`window.open` | CHANGE-015でWebView2上の失敗を実機確認済み。 |
| 別ウインドウでもstoreを完全に持ち、Undo履歴を個別に持つ | 2つの履歴が食い違い、Undo結果が直感と合わなくなる。 |

## 結果

### 利点

- キャンバスを覆わずにGradient Rampを編集できる。
- 今後ほかのパネルを別ウインドウ化する場合も同じ方式を再利用できる。

### 欠点・コスト

- 同期するsliceの追加・変更時は、同期キーの一覧とテストを更新する必要がある。
- 実際の表示可否はTauri実機（WebView2）でしか確認できず、Release Gateで確認する。
- 両ウインドウで同時に同じ値を編集した場合は後着の値が優先される。

## 再検討条件

- Tauri実機で、ブラウザー引数を一致させても極小ウインドウや未ロードが再現した場合。
- Tauri／WebView2がウインドウごとに異なるブラウザー引数を安全に扱えるようになった場合。
- 同期するsliceが大きくなり、イベント転送の負荷が操作に影響する場合。

## 実機確認で判明したこと

- 2026-09-26: Windows実機でブラウザー引数を一致させた別ウインドウが正常に生成されることを確認した。
- 当初の実装は変更のたびにpatchを即時送信していた。そのため、ドラッグ中にメインウインドウの処理が追いつかずイベントが滞留し、キャンバスへの反映に大きな遅れが出た（時間が経つと追いつく）。ACKによる流量制御を追加した。
